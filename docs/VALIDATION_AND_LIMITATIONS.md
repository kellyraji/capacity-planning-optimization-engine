# Validation plan and known limitations

## Current validation controls

The repository contains unit tests for capacity scaling, hourly data validation and forecasting horizon behaviour. The forecasting pipeline computes MAE and RMSE on a chronological holdout for its seasonal-naive benchmark. These checks do not establish full end-to-end validation against the source release.

## Validation checklist before publishing results

### Data
- [ ] Record source release, download date and partition coverage.
- [ ] Snapshot schema from actual downloaded files.
- [ ] Validate server-hour keys, duplicates, nulls and numeric ranges.
- [ ] Preserve relative time; label artificial timestamps.
- [ ] Reconcile aggregate server counts and GPU totals to source partitions.
- [ ] Test join cardinality before joining pod and server tables.

### Forecasting
- [ ] State that the current target is observed GPU inventory/capacity.
- [ ] Compare persistence and seasonal-naive benchmarks.
- [ ] Use chronological holdout and add rolling-origin backtesting.
- [ ] Report MAE/RMSE with units and validation interval.
- [ ] Review missing-hour policy, seasonal stability and horizon behaviour.

### Capacity and optimisation
- [ ] Calibrate utilisation, usable-capacity and safety-buffer assumptions.
- [ ] Calibrate server capacity and financial coefficients from documented sources.
- [ ] Reconcile solver objective with exported period-cost calculations.
- [ ] Test boundary cases, infeasibility and expansion limits.
- [ ] Add lead times, compatible resource classes and operational constraints before deployment use.

### Risk simulation
- [ ] Document rationale for each random input distribution.
- [ ] Run sensitivity analysis across plausible parameter ranges.
- [ ] Report uncertainty bands and seed.
- [ ] Label shortage probabilities as conditional model outputs.

## Known limitations

1. Current forecast uses server inventory; it does not forecast actual workload demand.
2. Optimisation is a simplified homogeneous capacity-expansion model.
3. Commercial cost inputs are illustrative units, not currency-validated costs.
4. Monte Carlo distributions are illustrative, not fitted to observed incidents.
5. Documentation changes do not demonstrate a successful full data download or end-to-end run.
6. No measured power, energy or carbon data is integrated; no environmental savings are claimed.
7. Pod aggregation is a schema-aware scaffold. Validate field semantics, units and aggregation operators against the exact release.

## Evidence rule

Publish a numeric headline only when reproducible from a tracked code path and saved output generated by an identified run. Label simulated, assumed and illustrative results explicitly.
